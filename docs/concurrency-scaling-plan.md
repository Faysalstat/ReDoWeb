# Concurrency Scaling Plan: Handling Simultaneous Generations

**Status:** Analysis complete, not yet implemented. Written 2026-09-20 in response to the question "if 10 people submit a generation at the same time, how does the platform hold up?" Updated the same day twice: (1) to fold in a follow-up request that enabled tiers should generate asynchronously/in parallel within a project, not one after another (gap 2 / plan F); (2) to add a fix for the generation-progress page's wait-time copy, which is now off by roughly two orders of magnitude against real observed generation times of 20-30 minutes (gap 9 / plan G).

## Context

The Postgres-backed job queue (`queued_jobs`, replaced Celery+Redis 2026-09-06) is already race-safe for concurrent claiming via `SELECT ... FOR UPDATE SKIP LOCKED` (`backend/app/workers/queue.py:25-31`). The problem isn't correctness — it's **capacity**: exactly one process (`backend/app/workers/queue_worker.py`) polls and executes jobs, one at a time, for every user on the platform. Today, 10 simultaneous submissions all enqueue successfully and fast, then queue up behind each other and run fully serially — crawl → blueprint review → per-tier generation, each project taking low minutes — so the 10th user could wait roughly 9× a single project's runtime before their own job even starts.

That single-worker design was a deliberate, documented choice when it replaced Celery ("no concurrency loss from not sharding work across processes" — `queue_worker.py:1-5`), made when the app had no concurrent-user load to speak of. Scaling to real multi-user traffic means revisiting that capacity choice, plus a handful of smaller correctness/robustness gaps that only start to bite once multiple users overlap — and separately, tier generation *within* a single project also runs sequentially today (see gap 2 below), which compounds the same latency problem even for one user.

This plan does not touch the task-level "no auto-retry on task failure" policy (CLAUDE.md, deliberate — avoids projects stuck in an ambiguous half-retried state) or the tier/pricing/storage architecture. It's scoped to making existing behavior hold up under ~10 concurrent users without over-engineering (no message broker, no Kubernetes, no S3 migration).

## Gaps found, ranked by impact

1. **[Critical] Single worker process serializes all pipeline stages for all users.** `queue_worker.py:28-52` runs one `while True` loop calling `handler(**payload)` inline — no thread/process pool. While one project's task runs, no other queued job (any user, any stage) can be claimed. This is the primary reason 10 concurrent submissions degrade to a queue rather than running in parallel.
2. **[High] Tiers within a single project generate sequentially, not in parallel — and a failure silently drops the rest.** `tasks_blueprint.py:58-67` enqueues only `tier_keys[0]`, passing the rest as `remaining_tiers`; `tasks_generate.py:16,132-137` enqueues the next tier only after the current one *succeeds*. Two consequences: (a) even a single user's project takes N× as long as necessary when N tiers are enabled, compounding gap 1's queueing delay; (b) if an earlier tier's `generate_site()` call raises (line 72-82), the exception aborts the task *before* the "enqueue next tier" line is ever reached — so today, one tier failing means every tier after it in the chain silently never even attempts to run, with no error surfaced for those un-attempted tiers. Both `tasks_blueprint.py:58-61` and `routers/projects.py:68-71` already carry comments explicitly anticipating this should become "a parallel fan-out instead of the sequential `remaining_tiers` chaining" — this plan implements that.
3. **[High] Head-of-line blocking from a stuck AI call.** A single hung OpenRouter call can occupy the one worker for up to `generation_call_timeout_seconds` (360s) + a 30s hard-deadline backstop (`openrouter_client.py:27,41`, added after a real 30+ minute hang incident) — blocking every other user's job behind it for up to ~6.5 minutes. Multiplied across a queue of 10, this compounds badly.
4. **[High] No transient-error retry/backoff on OpenRouter calls.** `openrouter_client.py` has no handling for 429/502/503/504 — any such response immediately raises `OpenRouterError` and fails the whole task. At 10-concurrent-user load, transient rate-limiting from the provider becomes far more likely to actually occur than it does today at near-zero concurrency.
5. **[Medium, but escalates to a real, frequently-triggered bug once gaps 1+2 are fixed] Wallet spend idempotency race.** `backend/app/services/wallet_service.py:74-88` checks for an existing `idempotency_key` *before* acquiring the wallet's `FOR UPDATE` lock. Two concurrent calls with the same key (double-click, two tabs open on the same download) can both pass the check, then the second's insert hits the DB's unique constraint (`models/wallet.py:53`) and raises an unhandled `IntegrityError` → 500, instead of gracefully returning the existing transaction. No double-spend is possible (the constraint backstops it), but the request errors instead of succeeding idempotently. `downloads.py`'s `download_spend` path goes through the same function, so one fix covers both. **Critically, `generate_tier_task` also spends via this same function with a *project-scoped* (not tier-scoped) `idempotency_key=f"generation_spend:{project_id}"` (`tasks_generate.py:60`, comment at lines 45-51 explicitly anticipates this) — so once tiers fan out in parallel (gap 2's fix) across multiple workers (gap 1's fix), two tiers of the *same* project will routinely call `spend()` with the identical key at nearly the same time.** This turns the race from a rare double-click edge case into something that happens on close to every multi-tier project, making this fix a hard prerequisite for gap 2's fan-out, not an independent nice-to-have.
6. **[Medium] DB pool is unconfigured (SQLAlchemy defaults).** `backend/app/db/session.py:9` sets no `pool_size`/`max_overflow`/`pool_timeout` (defaults: 5 + 10 overflow = 15, 30s timeout). The shared Postgres instance (`G:\Standalone Services\postgres`, `max_connections=100`) is also used by 4 unrelated apps with no reserved budget for ReDoWebs. Adding worker processes (gap 1's fix) multiplies this — each process gets its own pool.
7. **[Medium] No disk-space safety net.** Local-disk `StorageBackend` (v1, by design) has no free-space check anywhere. 10 concurrent projects each generating output for multiple active tiers could exhaust disk with no warning or graceful rejection — confirmed via grep, no such check exists today.
8. **[Low, but confirmed by an explicit code comment] Per-project OpenRouter burst.** `blueprint_review.py:364-372` fans out up to 16 concurrent OpenRouter calls per project via `ThreadPoolExecutor` (`_worker_count`, capped "to bound simultaneous outbound OpenRouter connections"). The module docstring at `blueprint_review.py:5-7` explicitly justifies this as "safe under the queue worker's single-task-at-a-time processing" — i.e. the original author's safety reasoning assumes only one project's blueprint review ever runs at once. Moving to multi-worker (fix for gap 1) invalidates that documented assumption: with N workers, worst-case simultaneous outbound OpenRouter connections becomes up to 16×N, not 16. Not a correctness bug (concurrency here only affects latency per that same comment), but the stale comment should be corrected when A ships, and this is the concrete reason to roll out worker count conservatively rather than jumping straight to a large N.
9. **[High, UX] The generation page tells users the wrong wait time.** Real-world generations now take 20-30 minutes (confirmed by the user from actual usage), largely because tiers still generate sequentially (gap 2). But `generation-progress.component.html:22` hardcodes: `"This takes about 30–60 seconds · {{ formattedElapsed }} elapsed"` — off by two orders of magnitude. A user watching a 3-second estimate blow past 20 minutes will reasonably assume the app is broken and abandon or retry, generating duplicate load. The elapsed-time counter this copy references already exists and works (`elapsedSeconds` signal + `startTicking()`, `generation-progress.component.ts:88,141-146,285-289`) — this is purely a stale-copy problem, not a missing mechanism.

## Plan

Sequencing: **D (wallet idempotency fix) before F (tier fan-out)** — F is what turns D's race from theoretical to routine, so D must land first or in the same change. **B (DB pool) before A (multi-worker)** — raising worker count without headroom in the pool risks pool-timeout errors. F's parallelism benefit depends on A actually running multiple workers, though F's failure-isolation benefit (a failed tier no longer blocks later tiers from attempting) is worth having even with a single worker. C and E are fully independent and can ship in any order/parallel with the rest.

### A. Bounded multi-worker parallelism
- **Files**: `backend/app/workers/queue_worker.py` (add a worker-id tag to the existing `print()` log lines only — `claim_next_job`'s `SKIP LOCKED` already makes concurrent claiming safe, no logic change needed there); `backend/app/ai/blueprint_review.py:5-7` (update the module docstring — it currently states thread-level concurrency there is "safe under the queue worker's single-task-at-a-time processing," which stops being true once A ships; reword to note per-project connections are capped at 16 but total outbound connections now scale with worker count); `docs/INSTALLATION.md` step 2.5; add `backend/scripts/start_workers.ps1` to launch N background processes (`Start-Process`) for local/Windows dev, replacing the current single-terminal instruction.
- **Approach**: Run multiple OS-level instances of `python -m app.workers.queue_worker`, started conservatively rather than jumping straight to a large N — **start at N = 2**, confirm no OpenRouter 429s or DB pool timeouts under a realistic burst (see Verification), then step up to 3-4 if headroom allows. This staged rollout exists specifically because of gap 8: each project's blueprint-review phase can already burst to 16 concurrent OpenRouter calls, so total platform-wide outbound connections scale as roughly 16×N during overlapping blueprint-review phases — worth confirming empirically against OpenRouter's actual rate limits for this account before committing to a fixed N. Each project's own stages can never race each other regardless of worker count — stage N+1's queue row doesn't exist until stage N's task creates it (enqueue-on-success within the same transaction, per existing design) — so adding workers only adds *inter*-project parallelism, no new intra-project race risk.
- **Edge cases**: a crashed worker process just leaves N-1 running (no auto-restart, matching the existing no-retry philosophy) — an orphaned "running" `queued_jobs` row from a crash is a pre-existing, low-frequency gap, not solved here.

### B. DB connection pool sizing
- **Files**: `backend/app/db/session.py` (`create_engine` call), `backend/app/config.py` (new `db_pool_size`, `db_max_overflow`, `db_pool_timeout` settings so it's tunable without a code change).
- **Approach**: Set `pool_size=5, max_overflow=5, pool_timeout=10` per process. Sized for A's eventual ceiling (1 web process + up to 4 workers = 5 processes × 10 = 50 connections) even though A starts at N=2 — so no re-tuning is needed as A's worker count is stepped up. 50 connections is well within the shared instance's 100-connection budget, leaving headroom for the other 4 apps on that Postgres instance. Lowering `pool_timeout` from the 30s default to 10s makes pool starvation fail fast and visibly rather than silently stalling a request.
- **Edge cases**: document the "~50 connections for ReDoWebs" budget as a comment next to `create_engine` so a future worker-count increase gets re-evaluated against the shared instance.

### C. Transient HTTP-level retry/backoff for OpenRouter calls
- **Files**: `backend/app/ai/openrouter_client.py` — wrap the call sites in `chat_completion` and `vision_json_chat` with a new `_post_with_retry(...)` helper around `_post_with_hard_deadline`.
- **Approach**: Retry only `httpx.HTTPStatusError` with status in `{429, 502, 503, 504}` and `httpx.ConnectError`/`httpx.ReadTimeout` raised before the hard-deadline path fires. Max 3 attempts, exponential backoff (2s/4s/8s), honoring `Retry-After` on 429 when present. Exhausting retries still raises `OpenRouterError` exactly as today, so the task-level no-retry policy is untouched — this is resilience *within* one call attempt, not a task retry.
- **Edge cases**: never retry the hard-deadline `concurrent.futures.TimeoutError` path itself (a stuck connection shouldn't be retried — risks stacking hangs); never retry non-429 4xx (those are non-transient, e.g. bad request/auth).

### D. Fix the wallet/download idempotency race
- **File**: `backend/app/services/wallet_service.py::spend()` (single fix point — `downloads.py` calls through it, so this covers both).
- **Approach**: Reorder to **lock-then-check-then-insert**: acquire the `with_for_update()` wallet lock first, then do the `idempotency_key` check. Two concurrent calls with the same key now serialize on the wallet lock; the second proceeds only after the first commits, and its (now post-lock) idempotency check finds the row and returns early — no `IntegrityError` possible. Chosen over catching `IntegrityError` because Postgres aborts the whole transaction on a unique-violation, which would force `spend()`'s caller to roll back and retry in a fresh session — messier given `spend()` doesn't own commit/session lifecycle today.
- **Edge cases**: keep the existing "create wallet if missing" step working the same way, just after the lock is held.

### E. Disk-space safety net
- **Files**: new `check_free_disk_space()` helper (e.g. in a small `storage_service.py` or alongside existing storage-path helpers); called from `routers/projects.py` at submission (before `wallet_service.spend()`, so a rejected submission never charges a credit), and defensively again at the start of `tasks_crawl.run_crawl_task` / `tasks_generate.generate_tier_task`.
- **Approach**: `shutil.disk_usage(storage_root)`; reject with a clear 4xx if free space is below a new `min_free_disk_gb` config setting (default 2 GB). The defensive re-check at task start matters because other concurrent projects may have consumed space between submission and this job actually running.

### F. Fan out tier generation instead of chaining it
- **Files**: `backend/app/workers/tasks_blueprint.py::extract_blueprint_task` (lines 58-67 — replace the single `enqueue(..., tier_keys[0], remaining_tiers=tier_keys[1:])` call with a loop that enqueues one `generate_tier` job per key in `tier_keys`); `backend/app/workers/tasks_generate.py::generate_tier_task` (drop the `remaining_tiers` parameter and delete the "enqueue next tier" block at lines 132-137 — the "ready" status computation at lines 122-130 already works via set comparison against all `GenerationJob` rows for the project, so it needs **no change** and is already safe for jobs finishing in any order/concurrently); `backend/app/routers/projects.py` (line 165's `current_tier = next((job.tier for job in jobs if job.overall_status == "running"), None)` picks only the *first* running job — widen this to `current_tiers: list[str]` since multiple tiers can now be `"running"` simultaneously); update the three comments that describe the old sequential design and no longer will (`tasks_blueprint.py:58-61`, `tasks_generate.py:116-121`, `routers/projects.py:68-71,138-143`).
- **Approach**: At blueprint-extraction success, enqueue every enabled tier's `generate_tier` job up front (still within the same `db.commit()` at `tasks_blueprint.py:69`, so no new transaction handling needed) instead of just the head of the list. This is safe with no other code changes because: (1) the "flip to `ready`" logic in `generate_tier_task` already recomputes membership by querying all succeeded `GenerationJob` rows rather than assuming chain position, so whichever tier finishes last naturally sets `project.status = "ready"`; (2) the per-project generation-spend charge is already idempotent on `project_id` alone (`tasks_generate.py:60`), so multiple tiers' concurrent `spend()` calls collapse to one real debit — *provided* D ships first, since D's lock-then-check ordering is what makes concurrent calls with the identical key resolve safely rather than raising; (3) `GET /projects/{id}` (`routers/projects.py:147-165`) already surfaces each tier's output independently as it lands (`generations` list, `tiers_completed`/`tiers_total`), and the frontend (`generation-progress.component.ts`) already renders previews incrementally per tier rather than waiting for the whole project — so no frontend rendering logic needs to change beyond the `current_tier(s)` label tweak. As a side effect, this also fixes the existing bug where one tier's failure silently prevented every later tier in the chain from ever being attempted (see gap 2) — each tier now fails or succeeds independently.
- **Frontend**: `frontend/src/app/core/redowebs-api.models.ts` (`ProjectStatusResponse.current_tier?: string` → `current_tiers: string[]`), `generation-progress.component.ts` (lines ~155-158, join multiple tier labels, e.g. "Premium, Pro" instead of assuming one).
- **Edge cases**: with a single worker (before A ships, or if A is rolled back), fan-out still processes tiers one at a time in whatever order they're claimed — no behavior regression, just loses the parallelism benefit while keeping the failure-isolation one. If `tier_keys` is empty (no enabled tiers — shouldn't happen in practice since submission is gated on at least one active tier), the loop simply enqueues nothing, matching today's `if tier_keys:` guard behavior.

## Verification

- **A/B**: Start with N=2 worker processes locally (`start_workers.ps1`), submit several test projects in quick succession, confirm via `queued_jobs` rows / worker log tags that more than one project's stage is `running` at the same time, that DB connections don't exhaust (`SELECT count(*) FROM pg_stat_activity WHERE datname='redowebs'` stays comfortably under the new pool ceiling), and that no OpenRouter 429s appear in the worker logs during overlapping blueprint-review phases. Only step N up to 3-4 after this comes back clean.
- **C**: Manually simulate a 429/503 (e.g. temporarily point at a mock endpoint or monkeypatch in a debug script) and confirm retry/backoff fires and eventually succeeds or raises `OpenRouterError` after 3 attempts. Per the user's standing preference to trigger actual generation tests manually, this plan sets up the retry path but doesn't itself trigger real paid generations.
- **D**: Add/extend a unit test in `backend/tests/` that calls `spend()` twice concurrently (or sequentially with the same `idempotency_key`) and asserts the second call returns the same wallet state without raising — consistent with the existing testing bar for credit/wallet math (CLAUDE.md).
- **E**: Unit test `check_free_disk_space()` against a monkeypatched `shutil.disk_usage` for both above/below-threshold cases.
- **F**: With D already shipped and at least N=2 workers running (A), submit a project with 2 enabled tiers (`premium`+`pro`) and confirm via `queued_jobs`/worker logs that both `generate_tier` jobs are enqueued immediately after blueprint extraction (not one-after-another) and can be claimed by different workers; confirm `GET /projects/{id}` shows both tiers' `generations` entries once both finish, `tiers_completed == tiers_total`, and `status == "ready"` exactly once (not flapping). Add a unit test asserting exactly one `CreditTransaction` row exists for `generation_spend:{project_id}` after both tiers "complete" in a simulated concurrent call. Separately, add a regression test for the failure-isolation fix: simulate tier A raising in `generate_site()` and assert tier B's job is still enqueued/attempted (unlike today).
- **G**: Load the generation-progress page and visually confirm the new copy renders correctly at 0s, a few minutes, and past 20 minutes elapsed (the existing `formattedElapsed` getter already formats past 60s as `M:SS`, so no format change needed — just verify by fast-forwarding `elapsedSeconds` in a component test or waiting it out manually per the user's standing preference to trigger real generation runs themselves). Confirm the History-page link actually navigates to `/history` and that a project submitted, then abandoned mid-generation, is still resumable from there.

### G. Fix the generation page's wait-time messaging
- **Files**: `frontend/src/app/features/generation/generation-progress.component.html` (line 22, the stale `"This takes about 30–60 seconds"` string; lines 62-65, the existing "you can close this tab" panel copy).
- **Approach**: Three changes, all copy-only (no new state/mechanism needed — `elapsedSeconds`/`formattedElapsed` are already wired up and already displayed):
  1. Replace the line-22 estimate with an honest range, e.g. `"This usually takes 15–30 minutes · {{ formattedElapsed }} elapsed"`. Keep it a static range rather than a computed estimate for now — a real per-tier ETA would need historical timing data this app doesn't collect yet, and a wrong computed number is worse than an honest range.
  2. Extend the existing "you can close this tab" panel text (lines 62-65) with a concrete way back: link to the `/history` route (`app.routes.ts:15`, `HistoryComponent`) by name, e.g. "...come back — find it anytime from your [History](/history) page."
  3. Re-check this copy once F (parallel tiers) ships and real-world timing is observed — parallel tiers should cut the typical wait roughly in half (bounded by the slowest single tier instead of the sum of all tiers), so the range may tighten from "15–30" to something narrower once that data exists. Not blocking this fix on F — ship the honest range now, tighten later.
- **Edge cases**: none — this is a pure copy change with no logic branches. Note (not a requested change, flagged for awareness only): the cosmetic sub-status phrases (`SUBSTEPS` in `generation-progress.component.ts:33-53`, e.g. "Sketching the new layout…") cycle every 2.4s and will visibly repeat hundreds of times over a 20-30 minute wait — left as-is since it wasn't part of what was asked, but worth a look if it reads as repetitive in practice.
