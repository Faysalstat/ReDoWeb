# ReDoWebs

AI-powered website modernization platform. A user submits a URL to a small static website (≤20 pages, no server-rendered backend); the system crawls it, extracts a structured blueprint (`design.md`), and generates three tiered AI redesigns (Basic/Premium/Pro) the user can preview and pay credits to download.

## Settled decisions — do not re-litigate without the user's explicit sign-off

These were deliberately chosen after an extended requirements interview, sometimes overriding an initially "obvious" default. Don't silently swap them:

- **Backend framework is FastAPI, not Django** — despite Django's built-in admin being tempting for this project's heavy admin-panel requirements, the user explicitly chose FastAPI. **The admin panel is a hand-rolled FastAPI JSON API (`/api/v1/admin/*`, gated by `require_admin`/`User.is_admin`) plus a matching Angular admin SPA (`frontend/src/app/features/admin/`)** — not SQLAdmin (this doc previously said SQLAdmin, which was never actually adopted; corrected 2026-09-20 after confirming no `sqladmin` dependency or ModelViews exist anywhere in the codebase). As of 2026-09-20 it covers: cross-user project/generation-history browsing with per-job model/template/token/cost breakdown (`admin_analytics_service.get_token_usage_by_job`, since `Tier.generation_model`/`AIModelSetting` only reflect *current* config and can drift after a past job ran), user browsing with wallet/ledger, manual credit refunds/adjustments (`wallet_service.admin_adjust()` + `admin_credits_service.issue_adjustment()`, writing a `Purchase(source="manual_admin")` row alongside the ledger entry), per-tier generation-model and shared vision-model overrides, `ModelPricing` CRUD, and prompt-template upload/enable/disable/delete (see the prompt-templates bullet below). Since 2026-10-05 it also has a **Payments** page (`routers/admin/payments.py`, `services/admin_payments_service.py`; design in `docs/admin-payments-plan.md`): a read-only payment-mode banner (the mode stays an `.env` setting on purpose), all purchases (test purchases hidden by default), and three per-purchase actions that never move money at PayPal — **Re-check with PayPal** (`billing_service.recheck_purchase`, also detects dashboard refunds on completed purchases), **Take back credits** (refunded only, once per purchase via ledger key `refund_clawback:{id}`, capped at the balance, writes nothing at balance 0) and **Mark as failed** (pending > 24h, re-checks first and refuses if the buyer actually paid). Admins never issue PayPal refunds from the app (user decision). Admin promotion stays CLI-only (`backend/scripts/promote_admin.py`), never exposed over HTTP.
- **Credits, not multi-model tiers**: tiers are *prompt-strategy variants* of the *same* LLM (via OpenRouter), not different models. Tier differentiation is a prompt-engineering/rubric problem, tuned empirically (Milestone 10 in the plan).
- **Tiers are dynamic, not a fixed Basic/Premium/Pro enum**: tiers live in a `tiers` table (key, label, is_active, sort_order, download_credit_cost) that admins can enable/disable/rename/reorder/price. Disabled tiers are skipped entirely during generation. **`pro` and `premium` are both currently `is_active=true`** in the live DB (`basic` is not) — see `backend/app/services/tier_service.py`, which is the one place tier-enabled logic lives; don't hardcode tier lists elsewhere. Note: `premium` has real generation history but only one project has ever been submitted since it was enabled (found 2026-09-16 while debugging what looked like a "premium doesn't generate" bug — it wasn't one, premium just hadn't been exercised).
- **Unified credit wallet**, ledger-based (`credit_transactions` table is the source of truth, `credit_wallets.balance` is a denormalized cache) — not a simple counter. Race-condition-safe spend uses `SELECT ... FOR UPDATE` row locking. See implementation-plan.md for why. `wallet_service.spend()` acquires this lock **before** checking `idempotency_key` (not after, fixed 2026-09-20) — two concurrent calls with the same key now serialize on the lock instead of racing to insert it, which matters once tiers fan out (above) and can call `spend()` with the same project-scoped key at nearly the same time from different workers.
- **3 free signup credits are intentionally never enough to download anything** (cheapest download tier costs 3, but 1 credit is always spent on the initial generation first) — downloads always require a paid top-up. This is deliberate, not a bug.
- **>20 page sites are rejected outright**, not silently truncated to the first 20 pages (raised 2026-09-17 from an original 3, at the user's explicit request — this doc previously said "3" while `config.py`'s `max_pages` was already 5, a pre-existing doc/code drift now reconciled at 20 in both places). Crawling catches every page up to the cap (`crawl_service.run_crawl`/`blueprint_extraction.py` are unchanged and stay cheap regardless of page count), but the expensive AI blueprint-review step (`blueprint_review.py`) only ever reviews the home page during the initial free/paid-tier preview run — see the "Generation is scoped to the home page only" bullet below for how the rest of a multi-page site gets built.
- **No domain-ownership verification** before crawling — legal/ownership risk is mitigated only by a mandatory ToS checkbox at submission plus logging every submission for abuse/DMCA response. This was a conscious risk trade-off, flagged and accepted by the user, not an oversight.
- **The blueprint is a structured JSON schema, not freeform markdown** — `blueprint_extractor.py`/`design.md`-as-source-of-truth are gone (2026-08-27 rewrite). `blueprint_extraction.py` (deterministic, no AI) maps a crawled page into `scraped.json` against a schema of ~14 named sections (hero/about/services_features/faq/cta_section/footer/testimonials/gallery_portfolio/team/pricing/stats_social_proof/credentials_awards/contact/blog_news) split into **Mandatory** (safe to AI-draft if missing — marketing copy, not a factual claim) and **Optional/no-fabrication** (left empty if the source lacks it, enforced in code not just prompted — testimonials, pricing, team, stats, credentials, contact, blog, gallery). **The schema is a template, not an exhaustive contract**: real content that matches no named section is preserved under its own site-derived heading in `additional_sections` rather than dropped or force-fitted into the wrong bucket, and a small widget-signature registry (`WIDGET_EXTRACTORS`) independently detects known page-builder components (e.g. an Elementor testimonial-carousel) that have no governing heading at all, which the heading-anchored block model would otherwise miss entirely. `blueprint_review.py` then runs two concurrent OpenRouter calls (`ThreadPoolExecutor`, Celery task still synchronous/`--pool=solo` on Windows) producing `blueprint.json` in the same schema shape: a vision **meta call** (site_name/tagline/fonts/tone off the logo image, degrades gracefully to the heuristic values on failure — every meta field has a working fallback now, so a failed call no longer fails the whole task) and a text-only **content call per page** (reviews only the Mandatory sections + `additional_sections`, code-enforced merge that never lets the model touch image fields or invent a new `additional_sections` key not already in `scraped.json`). Both calls' no-fabrication instruction is absolute: never draft testimonials, stats/numeric claims, pricing, credentials/awards, team members, or contact details. `blueprint_legacy_compat.py` renders `blueprint.json` back into a `design.md`-shaped text blob purely so the still-unchanged `site_generator.py` keeps working — `design.md` is now a derived artifact, not the source of truth. Full design: `docs/blueprint-json-pipeline-plan.md`; manual testing flow (including the DB-free `/api/v1/debug/*` routes): `docs/blueprint-pipeline-experiment-plan.md`.
- **Generation is scoped to the home page only for the initial tiered preview** — `site_generator.generate_site()` still reads `design.md` and still supports a `template_override` param (used only by the debug route for `generate_site()` itself, never by real preview callers, which keep the random per-tier choice), but its system prompt constrains output to a single `index.html`/`style.css` regardless of how many pages the blueprint has. As of 2026-09-17 this is now also enforced upstream: `blueprint_review.py`'s `review_blueprint()` takes `page_indices`/`include_meta` params, and the real pipeline (`tasks_blueprint.extract_blueprint_task`) passes `page_indices=[0]` so the initial AI-review pass only ever costs one page's worth of calls, no matter how large the crawl was — `blueprint_extraction.py`'s deterministic `scraped.json` still holds every crawled page on disk, unused until later. **The rest of a multi-page site is a lazy, cached, no-extra-charge paid feature, not a deferred no-op**: the first time a user downloads a tier for a project with more than one crawled page, `downloads.py` enqueues `tasks_full_site.generate_full_site_task`, which AI-reviews the remaining pages (`review_blueprint(..., page_indices=range(1, N), include_meta=False)`), merges them into `blueprint.json`/`design.md` in place, and calls `site_generator.generate_full_site()` — a batched agent-loop run (a few pages per call, not all at once) that reuses the original preview's `template_used` (never re-rolled) and writes into `generated/{tier}/full/` (a sibling of the live preview dir, never overwriting it). Style continuity with the already-shown home page is enforced at the tool layer, not just prompted: `generation_tools.make_tool_dispatch()` takes `locked_files`/`append_only_files` params, so the full-site run's `index.html` is physically un-writable and `style.css` writes only ever append. The resulting `GenerationJob` row for this is `scope="full_site"` (vs. the original run's `scope="preview"`) — see `models/job.py`. Same `download_spend` idempotency key covers both, so there's no extra credit charge for unlocking the full site.
- **Payments are PayPal, not Stripe** (user decision 2026-10-05; Stripe was planned but never built). Users buy **admin-configurable credit packs** (`credit_packs` table, each pack carries its **own** price so bigger packs can be discounted — `cost_settings`' `usd_per_credit` is *not* a price, only the cost gate's estimate-to-credits conversion) via the PayPal Orders v2 API + JS SDK Smart Buttons, with **PayPal account or card** (`enable-funding=card`; Pay Later/Venmo disabled). Flow (`services/billing_service.py`, `payments/paypal_client.py` — plain `httpx`, no PayPal SDK): `POST /billing/paypal/orders` snapshots the pack into a `pending` `Purchase` and creates the order for exactly that server-side price → browser `onApprove` → `POST /billing/paypal/orders/{id}/capture` grants credits → `POST /billing/paypal/webhook` (signature-verified via PayPal's verify API, needs `REDOWEBS_PAYPAL_WEBHOOK_ID`) is the safety net for a closed tab. **Exactly-once crediting** rests on a `FOR UPDATE` lock on the `Purchase` row plus ledger idempotency key `purchase:{id}` (`wallet_service.grant_purchase_credits`, lock-then-check like `spend()`) — the browser capture and the `CHECKOUT.ORDER.APPROVED` webhook race on nearly every purchase, and PayPal's `422 ORDER_ALREADY_CAPTURED` is handled as success, not an error. Credits are only granted for a `COMPLETED` capture whose amount/currency match the snapshot; a timeout leaves the purchase `pending` (never `failed`); `failed` is not terminal (a buyer can retry a declined order with another card). Refunds are **marked only**, never clawed back automatically (PRD: manual via admin adjustment). Tier label/order/on-off/download cost are admin-editable on the Tiers & pricing page (`/admin/tiers`, `tier_service.update_tier`; the key is never editable; cost min 1, UI warns below 3). The frontend's `tierLabel()` shows the admin-set label (loaded once from public `GET /tiers`), falling back to the capitalised key. Full design: `docs/paypal-payments-plan.md`.
- **Local disk storage in v1**, behind a `StorageBackend` abstraction — S3 migration is explicitly deferred, don't build it prematurely.
- **Apple SSO is deferred**, but the `auth_identities` table (not columns on `users`) exists specifically so it can be added later without a schema rework.
- **No WebSockets** — job-status is polled via REST (~3s interval) by design, not an oversight.
- **Testing bar**: unit tests for credit/wallet math, tier pricing, PayPal webhook/capture handling, and auth/permission checks — plus, as established in practice during the structured-JSON blueprint pipeline build (2026-08-27), the *deterministic* pieces of the crawler/AI pipeline: heuristic classification logic (given a fixed HTML fixture, does it bucket into the right section), and the code-enforced safety nets around each AI call (does a merge function actually refuse a model-invented key, does the anti-fabrication verbatim-quote check actually reject a fabricated string) — these test the surrounding code's behavior with a fake/adversarial LLM response, not the AI's judgment quality. What's still **not** unit-tested, per the original intent of this rule: whether the AI's actual output is *good* (copy quality, whether a real site's heuristic classification is subjectively correct) — that stays manual/exploratory, don't over-invest in e2e tests for subjective AI output.
- **Site generation is an agentic tool-calling loop via OpenRouter, not a single-shot completion** — the user only has an OpenRouter key (no direct Anthropic key), and OpenRouter's wire format is OpenAI-compatible, not Anthropic's native Messages API, so Anthropic SDK features (Tool Runner, Managed Agents, the actual Claude Agent SDK) don't apply here. `site_generator.py` hand-rolls the tool-call loop (`_run_agent_loop`), giving the model `write_file`/`read_file`/`list_files` tools sandboxed to `generated/{tier}/`. Every tier picks one of `backend/prompts/*.txt`'s hand-authored design-strategy files at random and uses it as-is as the system prompt (they're already written as agent instructions) plus a code-appended constraint (no React/build tooling, plain HTML + Tailwind/Bootstrap via CDN). **As of 2026-09-20, these files are admin-manageable, not fixed at deploy time**: an admin can upload a new `.txt` file via the admin panel (`POST /api/v1/admin/prompt-templates`, category + name → server-constructed `{category}_{name}_prompt.txt`, written into `backend/prompts/` — never from the client-supplied filename, since this repo has a documented history of path-traversal bugs in file-writing code) and enable/disable/delete existing ones. A lightweight `prompt_templates` table (`backend/app/models/prompt_template.py`) tracks only filename/category/active-state/audit — the prompt *text* always stays a plain file on disk, never duplicated into the DB. A file with no DB row is treated as active by default (so the original hand-authored files keep working with zero backfill), and only gets a real row the first time an admin toggles it (`prompt_template_service.set_active`). `site_generator._select_template()` stays DB-free per its existing contract — it now takes an optional `candidates` filename list, resolved one layer up in `tasks_generate.py` via `prompt_template_service.get_active_template_filenames(db)`, so a disabled template actually stops being picked. `app/ai/postprocess.py` runs after the agent loop (alt-text fallback, OG tags, WCAG contrast check, `sitemap.xml`). **An AI-generated alternative ("recipe anchor" + `design_system.json`, via a separate `design_system_generation.py` module + `backend/prompts/recipes/*.md` library) was built, used briefly for non-`premium` tiers, and fully removed again (2026-09-16)** at the user's explicit request — it ran an extra per-project AI call that a single-tier project would pay for even when unused, and its resolved recipe name surfaced in ways that looked like a bug (an unused `design_system.json` sitting next to real template-based output). Don't re-add it without the user's sign-off; if revisited, thread it through per-tier the same way `model_config_service` threads model overrides, not a hardcoded tier-name constant.
- **`max_tokens` for generation must stay generous** (currently 16000) — an 8192 cap caused the model to truncate mid-tool-call while writing a full HTML page, producing invalid/incomplete JSON tool arguments that it then retried identically forever. If iteration limits are hit again, check `finish_reason` in the debug trace before assuming it's a prompt problem.
- **Frontend is Angular 20 (standalone components) + Tailwind CSS v4**, scaffolded in `frontend/`. Corrected 2026-09-21: this doc previously said the frontend implements only submit→progress→preview and nothing else — that was stale. `frontend/src/app/app.routes.ts` shows real, backend-wired routes for Google SSO login (`/login`, `/auth/callback`), project submission/progress (`/`, `/projects/:id`), generation history (`/history`), and the full admin panel (`/admin`, lazy-loaded, gated by `adminGuard`) — all of these have working backend counterparts and are fair game to extend. As of 2026-10-05, `/pricing`, `/checkout`, and `/settings/billing` are real too (PayPal credit packs — see the payments bullet below); `/pricing` is public, `/checkout` and `/settings/billing` are behind `authGuard`. `home.component.ts` uses a **submit-once-then-poll pattern**, not sequential per-step calls: `POST /api/v1/projects` enqueues the pipeline's first stage (the Postgres-backed job queue, not Celery — see the queue bullet below) and returns immediately, then the frontend polls `GET /api/v1/projects/{id}` every 3s (RxJS `timer`/`switchMap`/`takeWhile`) until a terminal status. The old per-stage endpoints (`crawl()`/`extractBlueprint()`/`generate()` in `redowebs-api.service.ts`) are marked `@deprecated` and kept only for backend debugging — don't build new frontend features against them.
- **Generated sites are served to the frontend via a `/preview` static-file mount** (`app.mount("/preview", StaticFiles(directory=storage_root/"projects"))` in `main.py`) plus CORS for `http://localhost:4200` — this is how the Angular app iframes generated output directly from disk, no download step needed for preview. If you edit `main.py` during a manual (non-`--reload`) dev session, remember to restart uvicorn — a forgotten restart after adding CORS caused a real "405 on OPTIONS preflight" bug that looked like a code problem but wasn't.
- **Postgres (SQLAlchemy 2.0 + Alembic) is wired for the crawl/blueprint/generate pipeline, but it's a dual-write, not a migration**: DB rows (`Project`, `CrawlSnapshot`, `CrawlPage`, `Asset`, `Blueprint`, `GenerationJob`, `GenerationOutput`) are created/updated for queryability/audit, while `metadata.json` and `design.md` on disk remain what `crawl_service`/`blueprint_extractor`/`site_generator` actually read from — those weren't refactored to read from DB in this pass.
- **A Postgres-backed queue table now orchestrates the real pipeline — Celery+Redis was removed (2026-09-06)**: Redis had no use in the app beyond being Celery's broker/result-backend (rate limiting is in-memory slowapi, auth is JWT), so the pipeline now runs on a `queued_jobs` table (`app/models/job_queue.py`) instead. `app/workers/queue.py` provides `enqueue()` (adds a row, no commit — callers enqueue the next stage in the same transaction as the current stage's status update) and `claim_next_job()` (Postgres `SELECT ... FOR UPDATE SKIP LOCKED`, the same row-locking style `wallet_service.spend()` uses). `app/workers/queue_worker.py` (run via `python -m app.workers.queue_worker`, replacing `celery worker`) polls and dispatches by `task_name` to `tasks_crawl.run_crawl_task` / `tasks_blueprint.extract_blueprint_task` / `tasks_generate.generate_tier_task`. `run_crawl` enqueues `extract_blueprint` on success; `extract_blueprint` then **fans out**, enqueueing one `generate_tier` job per enabled tier up front (not a chain) — each tier now succeeds or fails independently, and the "flip to `ready`" status logic in `generate_tier_task` recomputes membership via set comparison against all `GenerationJob` rows rather than assuming chain position, so it's correct regardless of finish order. Each task still updates `Project.status` and commits its own DB rows; **no auto-retry is configured on purpose** — any exception (transient or definitive) immediately marks the project `failed`/`rejected` via a broad `except Exception`, rather than half-building a retry policy that could leave a project stuck in an intermediate status forever (this is a task-level policy, separate from the transient-error retry/backoff `openrouter_client.py` does within a single call attempt — see below). **Multiple `queue_worker.py` processes can now run concurrently** (2026-09-20, see `docs/concurrency-scaling-plan.md`) — `claim_next_job()`'s `SKIP LOCKED` was already safe for this; `backend/scripts/start_workers.ps1 -Count N` launches N of them, each tagged with a `REDOWEBS_WORKER_ID` for log disambiguation. A project's own pipeline stages can never race each other regardless of worker count (a stage's queue row doesn't exist until the prior stage's task creates it), so more workers only add parallelism *across* projects and tiers, never within one stage. Start conservatively (N=2) and step up only after confirming no OpenRouter rate-limit errors — each project's blueprint-review step can already burst to 16 concurrent OpenRouter calls (`blueprint_review.py`'s `_worker_count`), so total outbound connections scale with worker count too. The DB pool (`db/session.py`, sized via `config.py`'s `db_pool_size`/`db_max_overflow`/`db_pool_timeout`) is explicitly tuned (not left at SQLAlchemy defaults) to stay within the shared Postgres instance's connection budget as worker count grows.
- **This machine runs an unrelated Docker Compose project also named `standalone`** (`G:\Web modernizer\iac\standalone`) occupying the default Postgres/Redis ports — that's why `standalone/docker-compose.yml` sets an explicit `name: redowebs` and remaps host ports to `15432`/`6380`. Separately, Windows has a reserved TCP port-exclusion range on this machine (5433–5532, check via `netsh interface ipv4 show excludedportrange protocol=tcp`) that silently fails binds — don't assume a "port already in use" error is the only reason a Docker port mapping can fail.

## Working style for this project

- No fixed deadline — correctness and getting the core crawl→blueprint→generate loop right matters more than speed. Milestone 2 in the implementation plan (the core loop, no auth/payments) is the highest-priority thing to get right first.
- This is currently a solo-developer project — keep documentation resumable across sessions (update `docs/PROGRESS.md` as milestones complete) rather than relying on in-session memory or todo lists.
